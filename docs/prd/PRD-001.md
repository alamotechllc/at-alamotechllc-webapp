# PRD-001 — Alamo Tech Customer Platform

**Status:** Draft  
**Project ID:** `at-customer-webapp`  
**Display name:** Alamo Tech Customer Application  
**Date:** 2026-10-23

This PRD defines the product. It does not approve implementation, and it does not build the modules it lists.

## Product

The product is the **Alamo Tech Customer Platform**.

It is not a RaaS dashboard. RaaS is one module inside the platform.

The future canonical hostname is `https://app.alamotechllc.com`. That hostname is not created by this PRD.

The public marketing site stays `https://alamotechllc.com` (`at-alamotechllc-website`). Development for that site stays `https://dev.alamotechllc.com`.

## Customers

An organization is the tenant. People belong to an organization. Everything a customer owns is scoped to that organization. Alamo Tech staff may operate across organizations only with an explicit platform role, and every cross-organization read or write is audited.

### Milestone acceptance, when a later build is approved

- A signed-in user lands in an organization.
- The server rejects a request for another organization's data.
- The UI can hide a module. Hiding it is not the authorization check.
- The RaaS area can show an empty Lead Capture state without calling a speculative API.
- DEV uses DEV identities and DEV data. DEV does not read production.
- Sign-in, sign-out, role changes, and denied access attempts are audit events.

## Lead Capture customer experience

Lead Capture is the first RaaS result. On the customer platform it means configuration, status, and results for that organization's Lead Capture service.

It does not mean the sales page. The sales page remains `https://alamotechllc.com/raas`. A later product page may exist at `https://alamotechllc.com/raas/lead-capture`. The customer path `https://app.alamotechllc.com/raas/lead-capture` is a different application.

Customer-visible Lead Capture information, when the module is built, is limited to what the RaaS API already allows that caller's role to read. This PRD does not add API routes.

## Authentication decision

People are identified with Firebase Authentication, using the model already specified in `at-alamotechllc-website` `docs/raas/11-mvp-security-model.md`.

The marketing site has no login. This application does not copy a session from that site.

- The API verifies Firebase ID tokens with the Admin SDK.
- Custom claims stay small. A tenant claim carries one organization id, not every organization an operator can see.
- Clients cannot write claims.
- Operational RaaS data stays behind the API. Firestore client access to that data stays denied.
- This application does not read the AlamoOS database or the MailGuard database.

The decision is recorded in `docs/architecture/overview.md`. No Firebase project is created by this PRD.

## Authorization

Roles:

- `platform_admin`
- `platform_operator` (the control-plane role `operator`)
- `tenant_admin`
- `tenant_user`
- `tenant_viewer`

Permissions sit under roles so later modules can extend them without a new role for every screen:

- `raas.view`, `raas.manage`
- `reports.view`
- `mailguard.view`
- `assessments.view`
- `organization.manage`
- `users.manage`

`tenant_user` is the member who can act on services they are granted. `tenant_viewer` is read-only. The first milestone does not invent extra permissions beyond this list.

## Integrations

- RaaS operations stay in `raas-control-plane` until a reviewed API is wired. Strategy: integrate, do not move the code.
- MailGuard stays the scanning engine. This platform may later show authorized fields. The field list is unknown.
- AlamoOS may later send customer-safe events. Internal prompts, agent internals, credentials, secrets, internal notes, privileged infrastructure, and internal operational data are never part of that contract.

## Deployment

DEV and MAIN are separate lifecycles: separate application, authentication, data, and backend. No production resource is created for this draft.
